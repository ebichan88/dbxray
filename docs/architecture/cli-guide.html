dbxray / cli

cli 読解ガイド

DBのカタログ（テーブル・カラム・制約・外部キー等のメタ情報）を読み、人が読むMarkdownのテーブル定義書・ER図と、機械が読むスキーマのスナップショット（JSON Lines）を出力するコマンドラインツールです。--checkを付けると、DBとコミット済みのスナップショットの差分を検知します。このガイドは、入出力と使っている技術の事前知識から始めて、実行の流れ、データの持ち方、中心のロジック、ソースごとの役割と繋がりまでを順に説明します。

  • 約12.8k 行main配下のJava（空行・コメントを含む目安）
  • 4層＋2presentation・application・domain・infrastructure と層の外のconfig・shared
  • 3 出力形式Markdown・スナップショット・参考情報（insights）
  • 2 DBMSPostgreSQL・Oracle。SQLはmapper XMLに分離

mainブランチ（0bb6bdd。PR #114まで）を読んで作成し、その後に入った--preview（関数・プロシージャが利用しているテーブルの出力。Issue #134・PR #137）の分を各章に追記しています（9.9節にまとめ）。コンソールの出力例は、ビルドしたjarを、docs/sample/postgres/ddl.sqlを流し込んだPostgreSQL 16に対して実行して採取したものです（長いパスは短く書き換えています）。Markdown・JSONの例は、コミット済みのベースラインdocs/sample/postgres/outputから引用しています。

先に掴んでおく6つの要点

  1. 一方向の変換器：DBのカタログとサイドカーYAMLを読み、Markdown・スナップショット・参考情報の3形式を書きます。DBへはSELECTしか発行しません。精度を固めている途中の機能は--previewを付けたときだけ動きます（1章・9.9節）。
  2. 層と依存の向き：presentation → application → domain ← infrastructure。ルールはdomainに、DB・ファイル・YAML・JSONとの接点はinfrastructureに、全体の組み立てはエントリーポイントとconfigにあります（3章）。
  3. 検証は入口で、報告はmainの1箇所で：設定・引数・出力先の誤りはDBへ接続する前に検証し、例外はmainだけが捕まえて終了コードに変えます（4章・5章）。
  4. 取得は2つの粒度：軽い情報（テーブル一覧・関連・トリガー等）は対象範囲全体を一括で、重い情報（カラム・インデックス・制約）はスキーマ・チャンク単位で取得して、書いたら捨てます（6章）。
  5. 出力形式ごとにSink：取得の順序は1つで、出力形式ごとのExportSinkがそれぞれの形で書きます。--checkはSinkをスナップショットの1つに減らして一時ディレクトリへ書くだけです（6章・7章）。
  6. テーブルキーで繋ぐ：カラム・関連・トリガー・付帯情報は、テーブルをオブジェクトで持たず「スキーマ名＋テーブル名」（TableKey）で指します。別々に取得した情報を後から1テーブル分に組み立てられるのはこのためです（8章）。

1事前知識：このツールの入力と出力

このツールは「DBのカタログ → 文書」の一方向の変換器です。文書に載せる内容の入力が2つ（DBのカタログとサイドカーYAML）、実行のしかたを決める入力が3つあり、出力は3つの形式とコンソールです。

通常実行

  • DBから取得し、3つの形式を出力先へ書く
  • 生成するファイルだけを作成・上書きする。DBから消えたテーブルのファイルは残るため、--rm-distで先に出力先を消せる
  • 終了コード：成功0、失敗2

--check

  • 取得は通常実行と同じ。スナップショットだけを一時ディレクトリに作り、出力先のsnapshot/とオブジェクト単位で比べる
  • 出力先には書かず、Markdown・ER図も作らない
  • 終了コード：差分なし0、差分あり1、失敗2。CIで「マイグレーション後の再生成・コミット忘れ」を検知する用途

--preview：固めている途中の機能は、付けたときだけ動く

精度や出力の形を、使った人の声を聞きながら固めている途中の機能は、--previewを付けて実行したときだけ動きます。今あるのはfunctionTableUsageの1つで、関数・プロシージャの定義本体から、利用しているテーブルと操作（C・R・U・D）を機械的に抽出します（9.9節）。結果は関数の定義書の「利用しているテーブル」と、参考情報のfunctionTableUsages.jsonに出ます。

  • 出力・挙動は互換性の対象にしません（CONTRIBUTING.mdの「互換性を約束する範囲」）。外すときは機能追加として扱います。
  • スナップショットは変えません。そのため--checkの結果には影響せず、--checkと同時に指定しても効果はありません（その旨を表示します。7章）。

出力先の構成

出力はすべてoutput.path（未指定なら./output）の下に、DBごとのディレクトリに分けて置かれます。同じ出力先へ複数のDBを出力しても混ざりません。

│   ├─ README.md                         一覧へのリンク集

│   ├─ erDiagramList_{DB名}.md           スキーマ別ER図の索引

同じ取得結果から3つの形式を作る

Markdownは人が読む最終成果物、スナップショットは機械が読む中間表現です。どちらもDBから1回取得した同じデータ（1テーブル分ならTableDefinitionContent）から作るため、内容は食い違いません。スナップショットは実行のたびに変わる生成日を含まないため、DBが変わらなければ何度実行しても同じ内容になり、--checkが日付で差分を出しません。観点はスキーマの事実ではなく「見せ方」なので、スナップショットには含めず、参考情報として別に出力します。関数・プロシージャが利用しているテーブルも、DBが持つ事実ではなく定義本体から抽出した参考値なので、同じく参考情報として出します。

2.1 Java 21：record・sealed・パターンマッチ

このコードベースのクラスの多くはrecordです（エンティティ・DTO・スナップショット・request）。recordのコンパクトコンストラクタ（引数リストを書かないコンストラクタ）で、受け取ったリストの複製や値の正規化をしています。

public record NodeLimit(int value) {
  public NodeLimit {
    value = Math.max(value, 0);   // 0以下は「上限なし」（0）へ揃える
  }
}

2.2 Google Guice：2段階で組み立てるDIコンテナ

DI（依存性の注入）は、クラスが使う部品を自分でnewせず、コンストラクタの引数で受け取る書き方です。誰に何を渡すかは、DIコンテナ（GuiceのInjector）が「束縛」の表に従って決めます。押さえる規則は4つです。

  • 束縛：bind(FileRepository.class).to(LocalFileRepository.class)のように、インタフェースに実装を対応させる。config.moduleの2つのモジュールに書く。
  • ジャストインタイム（JIT）束縛：束縛の無い具象クラスでも、@Inject付きのコンストラクタがあればGuiceがその場で作る。コントローラー・2つのユースケース・SchemaExportPipeline・OutputDirectoryValidatorはこれで作られる。
  • jakarta.inject.Inject：@InjectはGuiceのものではなく標準のものを使う。Guiceに依存してよいのはエントリーポイントとconfigだけ（ArchitectureTestが検査）。
  • 子のコンテナ：injector.createChildInjector(module)で、親の束縛を引き継いで束縛を足したコンテナを作れる。
// Dbxray.createController：DBへ接続するのはここだけ
final SqlSessionFactory sqlSessionFactory = MyBatisSqlSessionFactories.create(connectionSettings);
return injector
    .createChildInjector(
        new DatabaseDependentModule(
            DatabaseTypeDetector.detect(sqlSessionFactory), sqlSessionFactory))   // ここで接続して種別を判定
    .getInstance(ExportSchemaController.class);

接続を束縛の定義（configure()）の中で行わないのは、そこで失敗するとGuiceの例外に包まれて届き、「DBに接続できない」を利用者が直せる誤りとして報告できなくなるためです（DatabaseDependentModuleのJavadoc）。束縛の漏れ・@Injectの付け忘れは、本番と同じ手順でコンテナを組み立てるDbxrayModuleTestが検知します。

2.3 MyBatis：SQLはXML、結果はrecord

MyBatisは、SQLをXMLに書き、結果の列をJavaのオブジェクトへ詰めるライブラリです。このツールが発行するのはすべてSELECTで、更新はありません。

読むときに戸惑いやすい点が4つあります。

  • SQLのIDは文字列で組み立てる。mapper XMLの名前空間com.dbxray.domain.repository.postgresql.CatalogRepositoryはJavaのクラス名に見えますが、そういうインタフェースはありません。AbstractCatalogRepositoryが「名前空間＋.＋ID」を文字列で作ってsession.selectListに渡します。IDEで定義へ移動できないので、ID（selectTableInfo等）の文字列でmapper XMLを検索してください。
  • 両方のmapperを常に読み込む。mybatis-config.xmlはPostgreSQL用・Oracle用の両方を登録し、DatabaseTypeの名前（postgresql・oracle）で名前空間を選びます。
  • 引数はschemaList・tableListの2つだけ。XMLの<if>で、リストが空なら絞り込み自体を外します。そのため空のリストでselectColumnListを呼ぶと全テーブルのカラムを取ってしまうので、Java側で空を弾いています。
  • 列とrecordは名前で対応する。SQLの別名（AS "schemaName"）とDTOのコンポーネント名を、mybatis-config.xmlのargNameBasedConstructorAutoMappingで対応させます。resultType="TableDto"はtypeAliasesで付けた短い名前です。
// AbstractCatalogRepository（要約）
baseSqlPath = "com.dbxray.domain.repository." + databaseType.id() + ".CatalogRepository.";

try (SqlSession session = sqlSessionFactory.openSession()) {     // 呼ぶたびにプールから接続を借りる
  return session.selectList(baseSqlPath + sqlId, Map.of("schemaList", schemaList, "tableList", tableList));
} catch (PersistenceException e) {
  throw new RuntimeException("Failed to select: " + baseSqlPath + sqlId, e);   // どのSQLかを添えて包む

2.5 JSON Lines と Jackson

スナップショットは、1行に1オブジェクトのJSONを並べたJSON Lines（.jsonl）です。1テーブルが1行なので、gitの差分がそのままオブジェクト単位の差分になり、--checkも行をオブジェクトとして突き合わせられます。JSONへの変換はJacksonSnapshotSerializerが行い、次の性質に依存しています。

  • 項目の順序が固定：recordのコンポーネントの宣言順に出力される。同じ内容からは常に同じ文字列になる（差分検知の前提）。
  • 空は出力しない：JsonInclude.Include.NON_EMPTYで、null・空文字・空リストの項目を省く。真偽値のfalseは省かない。
  • 日本語はそのまま：非ASCII文字をエスケープしない（git diffで読めるように）。
// snapshot/testdb/database.json
{"formatVersion":1,"name":"testdb","dbms":"PostgreSQL","majorVersion":16}

DBの版はメジャーバージョンだけを持ちます（DatabaseEntity.majorVersion）。マイナー版を更新したときに、--checkが差分を報告しないようにするためです。

domain層はJacksonに依存しません。変換のインタフェースSnapshotSerializerをdomainに置き、Jacksonを使う実装をinfrastructureに置いています。

2.6 log4j2 と ArchUnit

  • log4j2（log4j2.xml）：ログを、実行したディレクトリからの相対のvar/log/dbxray.logへ書く。既定のレベルは、このツール（com.dbxray）がINFO、ライブラリがWARN。INFOには、接続先のDBMS・ドライバの版、件数、処理時間のような、1回の実行で数件に収まる調査の起点だけを出す。MyBatisは実行したSQL（DEBUG）と取得した行（TRACE。DBのメタ情報そのもの）をこのツールのパッケージ配下のロガーへ出すため、既定では残さず、調べるときに-Ddbxray.log.level=debug（またはtrace）で上げる。このツールのWARNだけは、標準エラーへも[warn]:付きで出す。処理結果の[result]:はロガーを通さずSystem.outへ直接出す。
  • ログに出さないもの：パスワード、接続URL、CLI引数・設定値の値、設定ファイル・サイドカーYAMLの内容を引用するライブラリの例外メッセージ。メッセージの改行は%enc{%m}{CRLF}で\n・\rへ置き換え、DB由来の文字列（関数の定義等）で偽のログ行を作らせない。
  • ArchUnit（ArchitectureTest）：レイヤーの依存方向や置き場所などの規約を、単体テストとして検査する。違反するとビルドが失敗する。規約の一覧は3章。

サンプルDBに対して通常実行したときの、既定のレベルのログファイルの全体です（日時とスレッド名を省き、長いパスを短くしています）。

3全体像と読む順

com.dbxrayの下は、4つの層と、層の外の2つ（config・shared）に分かれます。依存の向きはpresentation → application → domain ← infrastructureで、domainは他のどの層にも依存しません。DB・ファイル・JSONとやり取りするインタフェースをdomainに置き、その実装をinfrastructureに置く（依存関係逆転）ことで、外部に触れるコードをドメインの外へ出しています。

層・パッケージひとことで

  4. ExportSinkと3つの…SinkFactory：出力形式ごとに「いつ何を書くか」（6章の表）。
  5. domain.model.target：ExportTargets・TableDefinitionContent・TableScope。取得したデータを組み立てる単位です（8章）。
  6. domain.model.table・relation：TableKey・ForeignKeys・ForeignKeyGroups・Cardinality。関連とER図のルールです（9章）。
  7. 関数が利用しているテーブルの抽出（--preview）：FunctionTableUsageAnalyzer→FunctionBodyLocator→TableReferenceScanner→SqlLexerの順に、9.9節の図と合わせて読みます。
  8. 気になる出力のWriter→Templates：たとえばTableDefinitionWriter（セクションの順）→TableDefinitionTemplates（各セクションの組み立て）。
  9. infrastructure：AbstractCatalogRepositoryとmapper XML、SidecarYamlRepository。
  10. 入口の検証：CliArguments・DbxrayProperties・ConnectionSettings・FailureReporter（5章）。

4起動から終了までの流れ

Dbxray.mainは、処理全体を1つのtry-catchで囲み、次の順に進みます。前半（1〜6）はDBへ接続せずに入力を検証し、後半（7〜11）で接続して出力します。入力の誤りを接続より前に報告するのは、DBに接続できない環境（接続情報の誤り・DBの停止中）でも、設定の誤りに先に気付けるようにするためです。

// Dbxray.run（通常実行。runCheckも同じ形）
System.out.println("Starting output of database documents. …");
cliArguments.requireKnownArguments();
final ConfigFile configFile = ConfigFile.load(cliArguments.configPath());   // 設定ファイルは1回だけ読む
final ExportSchemaRequest request =
    DbxrayProperties.of(configFile, cliArguments.settingOverrides())
        .toExportSchemaRequest(cliArguments.isRmDist(), cliArguments.isPreview());
final Injector injector = createInjector();
injector.getInstance(OutputDirectoryValidator.class).validate(request);
final ConnectionSettings connectionSettings = connectionSettings(configFile, cliArguments);   // ConnectionSettings.merge
final ResultDto resultDto = createController(injector, connectionSettings).execute(request);
System.out.println(resultDto.resultMessage());
return ExitStatus.SUCCESS;

入口で文字列を型に変える

設定値は生の文字列のまま深い層へ渡しません。DbxrayPropertiesが空白を除き、整数へ変換し、出力対象の条件をTargetSelection.ofで型（TableScope・OutputObjectTypeの集合）へ変換します。誤りは1件ずつではなく、見つかった分をまとめて報告します。結果はrequestのrecordになり、エントリーポイント→コントローラー→ユースケースの3層を分解・再構築されずに通ります。

5失敗の扱いと終了コード

失敗は3種類に分けて扱います。どれに当たるかで、表し方と利用者への報告が変わります。

種類例表し方報告
利用者が直せる誤り設定・引数の誤り、出力先が危険、DBに接続できない、非対応のDB、サイドカーYAMLが無い・読めないUserCorrectableException（設定ファイルの誤りは派生のInvalidConfigurationException）。何を直せばよいかをメッセージに書く[result]:FAIL＋メッセージ。ログにスタックトレースを残さない
想定外の失敗I/O・SQLの失敗、不具合、JVMのエラー非検査例外のまま伝える[result]:FAIL＋メッセージ＋ログの場所。ログにスタックトレース
業務上の結果--checkの差分、孤児付帯情報、除外した関連例外にせず値で返す（DiffResult・ConsistencyNotice）差分の報告、警告のログ（[warn]:）

捕まえるのは main の1箇所だけ

コントローラー・ユースケースは例外を捕まえません。mainがThrowableまで捕まえてFailureReporterに渡し、終了コード2で終わります（Errorまで捕まえるのは、捕まえないとJVMが終了コード1で終わり、--checkの「差分あり」と区別できなくなるため）。途中の層でcatchしてよいのは、次の3つの場合だけです。

目的実例
検査例外を非検査例外で包むLocalFileRepository（IOException→UncheckedIOException）、AbstractCatalogRepository.select（どのSQLかを添えてRuntimeExceptionで包む）
下位の例外を利用者が直せる誤りへ置き換えるDatabaseTypeDetector（接続の失敗）、SidecarYamlRepository（YAMLの構文誤り）、DbxrayProperties（TargetSelectionのIllegalArgumentException）、ConfigFile（YAMLの構文誤り。文言はYamlSyntaxErrors）
フォールバックするSidecarYamlRepository（誤った観点を、警告して読み飛ばす）

包むときは原因（cause）を渡し、tryの範囲は置き換えたい呼び出しだけに絞ります。例外はYAMLの構文誤りで、SnakeYAMLの例外のメッセージは誤りの行をそのまま引用するため（設定ファイルに誤って書いたパスワードが画面とログに出得る）、YamlSyntaxErrorsで種類と位置だけの文言にし、原因は渡しません。UserCorrectableExceptionを投げるのは、入口（CLI引数・設定・出力先の検証）と、利用者の入力・実行環境に触れるインフラ（DBへの接続・サイドカーYAMLの読み込み）だけで、domain・applicationでは投げません。

6取得と書き出しの段取り（SchemaExportPipeline）

通常実行のユースケースは短く、取得と書き出しの段取りをSchemaExportPipeline（パッケージプライベート）に任せています。--checkのユースケースも同じパイプラインを使い、違いは渡すExportSinkのリストだけです。

// ExportSchemaUsecase.exportSchema
final Path outputBaseDir = outputPathResolver.resolveOutputBaseDir(request.outputPath());
final ExportTargets targets =
    schemaExportPipeline.fetchTargets(request.targetSelection(), request.sidecarPath());   // 一括取得
final DiagramBoxes diagramBoxes =
    schemaExportPipeline.fetchDiagramBoxes(targets, request.chunkSize());                // ER図の箱
if (request.rmDist()) {
  removeOutputBaseDir(outputBaseDir);   // 取得に成功してから消す
}
schemaExportPipeline.export(
    targets,
    List.of(
        markdownSinkFactory.create(
            outputBaseDir,
            NodeLimit.of(request.erDiagramMaxNodes()),
            request.erDiagramDistance(),     // テーブル定義書のER図の描画距離（9.7節）
            diagramBoxes,
            targets.foreignKeys()),
        snapshotSinkFactory.create(outputBaseDir),
        insightSinkFactory.create(outputBaseDir)),
    request.chunkSize(),
    request.previewFeatures());   // --previewで有効にした機能。空なら利用テーブルの抽出をしない（9.9節）

軽い情報は一括で、重い情報はチャンクで

対象スキーマ全体を一度にメモリへ載せないよう、取得を2つの粒度に分けています。テーブル一覧・関連・トリガー等は1件が軽く、ER図や被参照情報でスキーマ・チャンクをまたぐ参照を解決するのに全件が要るため、最初に一括で取得して最後まで持ちます。カラム・インデックス・制約はテーブル数に比例して重くなるため、スキーマごと・chunkSize件ごとに取得し、書き出したら捨てます。

8データの持ち方

8.1 テーブルキーで繋ぐ

このツールはDBを読むだけなので、更新の整合性を守るための集約や状態遷移はありません。代わりに設計の軸になっているのがテーブルキー（TableKey＝スキーマ名＋物理テーブル名）です。カラム・制約・トリガー・関連・付帯情報は、所属するテーブルをオブジェクトの参照ではなくテーブルキーで指します。だから、別々のSQLで、別々の時点で取得した情報を、後からテーブルキーで引き合わせて1テーブル分に組み立てられます。

ForeignKeysとViewReferencesは索引を2つ持ちます。ForeignKeysは、参照元のテーブルキーで引く索引（自分が参照している関連）と、参照先のテーブルキーで引く索引（自分を参照している関連＝被参照）です。被参照の索引からは自己参照を除きます（定義書の「外部キー情報」と「被参照情報」に二重に載らないように）。ViewReferencesも同じ形で、ビューのテーブルキーで引く索引（belongingTo。ビューが参照するテーブル）と、参照されるテーブルのテーブルキーで引く索引（referencingTo。そのテーブルを参照しているビュー）を持ちます（9.8節）。

8.2 取得の単位と、1テーブル分の組み立て

一括取得したExportTargetsと、チャンク単位で取得したTableDetailから、テーブルごとにTableDefinitionContent.assembleで「1テーブル分の出力内容」を組み立てます。これがテーブル定義書1ファイル、スナップショット1行に対応する書き出しの単位です。

9.2 関連の合流と突き合わせ（ExportTargetConsistency）

外部キー制約を張らないDBでは、カタログの外部キーだけではER図がほとんど空になります。そこでサイドカーで宣言した論理リレーションを、物理の外部キーと同じ集合（ForeignKeys）へ合流させます。合流させることで、ER図のグループ分割（連結成分）、スキーマ跨ぎの関連の抽出（crossSchema）、被参照（referencingTo）に、追加の実装なしで反映されます。読み手が「DBに制約がある」と誤読しないよう、区別は2箇所で付けます。

  • 定義書のセクション：physicalBelongingToは「外部キー情報」へ、logicalBelongingToは「論理リレーション情報」（注意書き付き）へ。
  • ER図の線種：RelationTypeが線種を持ち、物理は実線--、論理は破線..。

外部キーそのものは「関連がある」ことしか示しません。多重度は、参照元（子）の外部キー列に付いた制約から機械的に決めます。SQLが2つの真偽値を返し、ForeignKeyDto.toEntityがCardinality.of(unique, mandatory)で多重度にします。

9.4 ER図の出し分け（ForeignKeyGroups・RenderingPlan）

Mermaidは大きすぎる図を描けないため、スキーマ別ER図1枚のテーブル数に上限（erDiagramMaxNodes、既定80、0以下は上限なし）があります。「ノード」は関連を持つテーブルで、関連の無いテーブルは図に描きません（全テーブルはテーブル一覧に載る）。ページ構成はForeignKeyGroups.composeが1回で決め、各ページで描くか省くかはForeignKeyGroup.planRenderingが決めます。Writer・テンプレートはその結果に従うだけです。

  • 連結成分（connectedComponents）：外部キーの両端を同じまとまりとして併合するUnion-Find（経路圧縮付き）。a→bとb→cは1つの成分になります。並びはノード数の降順、同数なら先頭のテーブル名の昇順で、何度実行しても同じです。
  • まとめ直し（pack）：成分ごとに1ページにすると2テーブルだけの図が大量にできるため、上限に収まる限り複数の成分を同じページに入れます（先頭から空きのあるグループに入れる貪欲法）。同じページの成分同士は線で繋がらないので、関連を誤読するおそれはありません。
  • 分けても1つにしかならない場合は、スキーマのページと同じ内容のグループページができるだけなので、分けずにSingleにします。この場合は上限を超えているのでOmitになり、図の代わりに外部キー一覧を載せます。
  • 観点ページは人が選んだまとまりなので分けません（ViewpointContent.relationsにplanRenderingだけを使う）。テーブル定義書のER図は分割せず、上限は描画距離を縮めるかの判断にだけ使います（9.7節）。

9.5 ER図の箱に何を表示するか（DiagramBoxes）

ER図はチャンクより前（writeOverview）に書きますが、箱にはカラムを表示します。そこでfetchDiagramBoxesが、関連を持つテーブルのカラムだけをスキーマ・チャンク単位で別に取得し、DiagramBoxes.Builderが関連カラム（関連の参照元・参照先として使われるカラム）だけを残して他を捨てます。

  • relationColumnsOf(drawnRelations)は、その図に描く関連で使われるカラムだけをテーブルごとに返し、参照元のカラムにFKを付けます（DiagramColumn）。
  • テーブル定義書のER図では、自テーブルだけは全カラム（TableDetailのカラム）を表示し、相手のテーブルは関連カラムだけを表示します。
  • 箱の表示名はMermaidSupport.assignLabelsが決めます。ふつうはテーブル名で、同じ図の中に同名のテーブルが複数のスキーマにあるときだけスキーマ.テーブルにし、論理名があれば「（論理名）」を付けます。
  • Mermaidの識別子は記号を_に置き換えるため、別のテーブルが同じ識別子になり得ます。スキーマ別ER図ではErDiagramTemplates.assignNodeIdsが_2・_3を付けて重複を避けます。

9.6 長い表のページ分割（PagedSectionWriter）

GitHubで表として表示できる行数には限りがあるため、行が多くなり得る一覧はすべてPagedSectionWriterを通して書きます。3,000行以下なら本体ページに表を埋め込み、超えるなら{本体のファイル名}_{n}.mdへ分けて本体にはリンクだけを載せます。行の文字列はページ単位で作り、全行分を同時にメモリに持ちません。対象は、テーブル一覧、ER図の掲載テーブル・外部キー一覧、スキーマ跨ぎの外部キー、トリガー/関数/シーケンス/型の一覧、観点の所属テーブル・観点一覧です。

9.7 テーブル定義書のER図の描画距離（DiagramNeighborhood）

テーブル定義書のER図は、既定では自テーブルの関連だけを描きます。設定のoutput.erDiagramDistance（--er-diagram-distance。1〜3、既定1）を上げると、関連先のテーブルが持つ関連まで描きます。どこまで描くかはForeignKeys.neighborhoodOfが決め、結果をDiagramNeighborhood（描く関連・描いた距離・指定された距離）で返します。

  1. たどる：自テーブルから関連を向きを問わず幅優先でたどります（参照先の索引と被参照の索引の両方を見る）。距離nなら、n−1段目までに到達したテーブルが持つ関連を、近い順に集めます。距離1は自テーブルの関連だけで、従来の出力と同じです。
  2. 縮める：図のテーブル数がerDiagramMaxNodes（NodeLimit）を超えるなら、超えなくなるまで距離を1つずつ縮めます。1でも超える場合は1で描きます（自テーブルの関連は省かない）。
  3. 知らせる：縮めた場合（isShortened）は、TableDefinitionTemplates.erDiagramが図の前にその旨を書きます。

サンプルのdepartmentを距離2で出力すると、関連先のemployeeが持つ関連（自己参照・attendance・employee_profile等）まで描かれ、図のテーブルは2から7に増えます。距離3と上限5を指定すると、上限を超えるため1段で描き、次の1文が付きます。

9.8 ビューが参照するテーブル（ViewReferences）

ビュー・マテリアライズドビューが参照するテーブル（ビューを含む）は、ビューのSQLを解析せず、DBが保持する依存関係から取得します（PostgreSQLはpg_depend・pg_rewrite、OracleはALL_DEPENDENCIES）。1件がViewReferenceEntity（参照する側のビューと、参照されるテーブル）で、集合がViewReferencesです。

9.9 関数・プロシージャが利用しているテーブルの抽出（--preview）

ビューが参照するテーブル（9.8節）と違い、DBは関数・プロシージャの依存関係を保持しません。そこで、定義本体（FunctionEntity.definition）のSQLを読んで、利用している出力対象のテーブルと操作（C・R・U・D）を機械的に拾います。DBが持つ事実ではない参考値で、精度にリスクがあるため、--previewを付けたときだけ動くプレビューの機能（PreviewFeature.FUNCTION_TABLE_USAGE。互換性の対象外）として入れています。

設計の軸は2つです。

  • 完全な構文解析はしない：「このキーワードの後ろの名前はテーブル」というきっかけと、前後の字句だけで判定します。構文解析器という依存を増やさず、構文の誤りや未対応の構文があっても止まらずに次の文から読み直せるようにするためです。呼び出している関数・動的SQLの中の参照は追いません（含まないことを定義書・MCPのツールの説明に書きます）。
  • どんな入力でも例外を投げず、入力の長さに比例する時間で終える：定義本体はDBでCREATEの権限を持つ人が書ける入力です。正規表現を使わず1文字ずつ読み（ArchitectureTestが検査。3章）、閉じていない文字列・コメントは例外にせず「読み切れなかった」印にします（コンパイルに失敗した本体もDBに残り得るため）。
  1. 字句に分ける（SqlLexer）：先頭から1文字ずつ読み、今いる場所が文字列・コメント・識別子のどれかを状態として持ちます。コメントと文字列は互いの中で効かない（文字列の中の--はコメントにならず、コメントの中の'は文字列を始めない）ため、同時に左から読まないと区別できません。規則はDBで違います（PostgreSQLはブロックコメントの入れ子・ドル引用符・E'…'、Oracleはq'[…]'・条件付きコンパイル）。そのため、DBMS種別を文字列ではなくDbmsのenumにして、switchで網羅的に切り替えます（DBMSを足すとコンパイルエラーで気付ける）。
  2. 本体を切り出す（FunctionBodyLocator）：引数・戻り値の型の見出しは解析しません（RETURNS SETOF t・p t%ROWTYPEをテーブルの利用と誤らないため）。実装はDBMSごとです。
    PostgreSQL（PostgresBodyLocator）：pg_get_functiondefは本体を常にドル引用符で囲むため、見出しの後の最上位のドル引用符の中身を字句に分け直します。SQL標準の本体（BEGIN ATOMIC … END・RETURN 式）は、最上位のBEGIN ATOMIC・RETURNから終わりまでです。
    Oracle（OracleBodyLocator）：単独の関数・プロシージャは見出しのIS・ASの後ろ全体です。パッケージのサブプログラムは、どれも定義にパッケージ全体が入っているため、PackageSubprogramsがBEGIN・CASEとENDの対応を数えて、パッケージ本体の最上位のサブプログラムの範囲を求めます。オーバーロードは引数名で対応付け、区別できなければすべての本体からまとめて抽出します（overloadsMerged）。
  3. 拾う（TableReferenceScanner）：字句を先頭から1回なめ、きっかけのキーワードの後ろの名前と操作をTableReferenceにします。文の状態（StatementState）は;と最上位のLOOPで丸ごと作り直すため、括弧の数が合わない文があっても次の文から読み直せます。動的SQL（EXECUTE・EXECUTE IMMEDIATE・DBMS_SQL等）は、含むことだけをDynamicSqlKindで示します。
  4. 照らす（FunctionTableUsageAnalyzer）：拾った名前のうち、出力対象のテーブル（ビュー・マテリアライズドビューを含む）と一致したものだけを残します。CTEの名前・変数・DUAL等や、出力対象外のスキーマ・テーブルはここで落ちます。テーブルごとに操作をまとめ、スキーマが決まったものをスキーマ名・テーブル名の順に、決まらないものをその後に並べます。

操作とそのきっかけ。操作はCrudOperationです。細かい規則（括弧で囲んだJOIN・インラインビューへのDML・MERGEの各WHEN等）は、TableReferenceScannerTestのケースの一覧がそのまま仕様になっています。

操作テーブルの名前の前にあるきっかけ
C（作成）INSERT INTO（OracleのINSERT ALL/FIRSTの各INTO、MERGEのWHEN NOT MATCHED THEN INSERTを含む）
R（読み取り）FROM（カンマ区切りの並び）・JOIN・APPLY（Oracle）・USING（DELETE・MERGE）。括弧で囲んだFROM (a JOIN b ON …)の先頭や、SELECT … FOR UPDATEもR
U（更新）UPDATE（MERGEのTHEN UPDATE、ON CONFLICT DO UPDATEを含む）
D（削除）DELETE（MERGEのTHEN DELETEを含む）・TRUNCATE

権限・トリガー・行ロックの構文にもINSERT・UPDATE・DELETE・TRUNCATE・EXECUTEの語が現れます（GRANT SELECT, TRUNCATE ON a, b TO r・CREATE TRIGGER … BEFORE TRUNCATE ON t・GRANT EXECUTE等）。直前の語（GRANT・ON・BEFORE等）でこれらを文として読まず、後ろのカンマ区切りの名前に操作を付けないようにしています。

スキーマ修飾の無い名前。スキーマは、定義から決まる場合だけ決めます。決まらない場合は、同じ名前の出力対象のテーブルがあるスキーマをすべて候補として持ち、候補が1つでもそのスキーマに決めつけません（SchemaResolution・TableUsage.schemaCandidates）。

DBMS定義から決まる場合決まらない場合（SchemaResolution）
PostgreSQL関数の属性としてSET search_pathが指定されていれば（FROM CURRENTは作成時の値に展開された形）、その並びの先頭から、出力対象のテーブルがあるスキーマにする（$user・pg_catalog・pg_tempは除く）。空（''）なら出力対象のスキーマが無く、DEFAULTは指定なしと同じ。本文中のSET文・set_config・EXECUTEで組み立てたSET文（変数でスキーマを渡す場合を含む）は読まない属性の指定が無ければ（本文で変更していても）実行時のsearch_pathで決まる（search_path）。指定がある場合に並びのどこにも無い名前は、出力対象外のものとして載せない

  • Writerは「何を・どの順で・どのファイルに書くか」の段取りだけを持ちます。Markdownの文字列を自分で組み立てません。
  • Templatesは副作用の無いstaticメソッドで、行・セクションの文字列を組み立てます。絞り込みやグラフの計算などのロジックは持ちません（それはdomain.modelの仕事）。
  • 種別をまたいで使う部品はwriter.templateにあります。MarkdownTemplateSupport（基本情報のセクション、表の1行row、リンクのセル[■](…)、エスケープescapeTableCell・escapePipe・escapeHtml・escapeInline、コードブロック・コードスパンの囲みcodeFence・codeSpan、真偽値のmarker）、MermaidSupport（識別子・表示名・属性・関連線）、PagedSectionTemplates（見出し・ページ送り・戻るリンク）です。

ファイル名と相対リンクの規則

ファイル名・パス・リンクを、テンプレートやWriterがString.format等で直接組み立てることはしません。出力先の絶対パスとドキュメント間の相対リンクが同じ規則を参照するため、ファイル名を変えてもパスとリンクが食い違いません。

DB由来の文字列を信頼しない

DB名・スキーマ名・テーブル名・コメント・関数やビューの定義は、ツールを実行する人とは別の人（DBでCREATE・COMMENTの権限を持つ人）が書ける入力です。引用符で囲んだ識別子には/・..・改行・HTMLも書けるため、出力・パスに使う箇所はすべて決まった部品を通します（docs/development/coding-guidelines.mdの「セキュリティ」）。サイドカーYAMLは利用者自身が書くため、説明文はMarkdownとしてそのまま出力します。

12変更するときの道しるべ

よくある変更ごとに、触る場所と確かめ方をまとめます。規約の原文はdocs/development/coding-guidelines.mdの「変更の種類ごとに必要な作業」にあります。

設定項目を1つ足すとき

  1. DbxrayPropertiesのSETTINGSに項目（設定ファイルでの位置・CLI引数名・値の形式）を足し、既定値と変換を書く。上書きのCLI引数はCliArgumentsがこの表から引く。
  2. 値をrequest（ExportSchemaRequest・必要ならCheckDocumentDiffRequest）に足し、使う層まで同じrecordで運ぶ。文字列のまま深い層へ渡さず、入口で型にする。
  3. 配布するconf/config.yml（全項目が未指定）に項目を並べ、docs/usage/cli.mdの設定の表（CLI引数の列を含む）を更新する。
  4. DbxrayPropertiesTest・CliArgumentsTestに、未指定・誤った値・上書きのテストを足す。

DBから取得する項目を足すとき

  1. PostgreSQL用とOracle用の両方のmapper XMLに列を足す。別名はDTOのコンポーネント名と同じにする。
  2. DTO（record）にコンポーネントを足し、toEntity()で値の形を揃える（無い値はDtoValues.textで空文字、連結された値はsplitでリスト）。業務ルール（既定値の決定・名前の生成等）はDTOやリポジトリに書かず、ドメインのメソッドに持たせる。
  3. エンティティに項目を足し、表示はテンプレートで（連結・エスケープ・○）。機械が読む必要があれば…Snapshotにも足す（値の形は8.3節、「空は出力しない」は2.5節）。
  4. ./gradlew integrationTestを実行し、PostgresCatalogRepositoryITに取得結果のテストを足す。Oracle側を変えたら./gradlew oracleIntegrationTestとOracleCatalogRepositoryIT。出力が変わるなら、verifyスキルの手順でベースラインを出し直す。

テーブル定義書にセクションを足すとき

  • 中身をTableDefinitionContent.assembleで1テーブル分に抜き出せるようにし、TableDefinitionTemplatesにセクションを返すメソッドを足して、TableDefinitionWriterの並びに加える。条件付きのセクションは空文字を返せば出力されない。
  • Writerの中でMarkdownの文字列を組み立てない。ファイル名やリンクはDocumentLocationsの規則を使う。

出力形式を足すとき

  • ExportSinkを実装したクラスと、それを作る…SinkFactoryをdomain.service.exportに作り、FactoryをDbxrayModuleに束縛して、ユースケースが渡すリストに加える。--checkで比較したいかどうかで、CheckDocumentDiffUsecaseのリストに加えるかを決める。
  • 配置の規則は…Locationsに、パスの解決はOutputPathResolverに足す（application層でパスの文字列を組み立てない）。

新しいドメインサービス・リポジトリを足すとき

  • コンストラクタにjakarta.inject.Injectを付ける。インタフェースと実装を分けたらDbxrayModuleに束縛を足す。DB種別で実装が変わるものだけはDatabaseDependentModuleへ。
  • 束縛の漏れはDbxrayModuleTestで分かる。ファイルを読み書きするならFileRepositoryを受け取る（Filesを直接使うとArchitectureTestが落ちる）。日付が要るならClockを受け取る。

プレビューの機能を足す・外すとき

  • 足す：PreviewFeatureにenumの値を足し、SchemaExportPipelineなどの有効かどうかで分かれる箇所だけが、request.previewFeatures()を見ます。--previewは機能を個別に選ばず全部を有効にするため、引数は増えません。出力が増えるファイルは、スナップショットに入れず、参考情報（insights/）か、--previewのときだけ出す節にします（スナップショットを変えると--checkの結果が変わるため）。
  • 互換性の扱い：プレビューの機能の出力・挙動は互換性の対象外です。docs/usage/cli.mdの「プレビューの機能」の表に足し、PRにpreviewラベルを付けます（CONTRIBUTING.md）。
  • ベースライン：--previewで変わる・増えるファイルだけを、差分のベースラインdocs/sample/{postgres,oracle}/output-previewに置きます。既定のベースラインと重複して持たず、結合テストが既定のものに重ねて比べます。サンプルの関数が変わったときも作り直します（verifyスキルの手順）。
  • 外す（--previewなしでも動くようにする）：機能追加として扱い、リリースノートで知らせます。実際の業務DBでの精度の確認を、外す前に行います。

関数の定義本体を読むコードを足す・変えるとき

  • 字句の規則はSqlLexerに、テーブルの判定はTableReferenceScannerに、DBごとの切り出しは…BodyLocatorに置きます。正規表現は使いません（ArchitectureTestが検出する）。どんな入力でも例外を投げず、入力の長さに比例する時間で終えるようにします。
  • 判定の規則を変えたら、TableReferenceScannerTest・FunctionBodyLocatorTestのケースの一覧に足します。範囲の切り出し（PackageSubprograms）を変えたときは、GeneratedPackagesTestも確かめます（後ろのサブプログラムすべてに波及するため）。
  • DBMSを足したら、Dbmsのenumに足します。switchが網羅的なため、DBごとに分岐している箇所がコンパイルエラーで分かります。

スナップショットの形式を変えるとき

  • スナップショットはmcp-serverとの契約です。互換性の無い変更ならDatabaseSnapshot.FORMAT_VERSIONを上げ、mcp-serverのSnapshotDirectoryReader.SUPPORTED_FORMAT_VERSIONを追従させる。
  • ./gradlew :mcp-server:testを実行する（SampleSnapshotContractTestがベースラインを読む）。項目の追加は互換で、mcp-serverを変えなくてもget_table等の結果に現れます（mcp-server 読解ガイドの6章）。

やってはいけないこと

  • 途中の層でcatchしてログを出し、再スローする（報告はFailureReporterだけが行う）。catch (Exception e)で広く包む（別の失敗まで同じ文言になり、原因も消える）。
  • domain・applicationでUserCorrectableExceptionを投げる（利用者が直せる入力の誤りは、ユースケースを呼ぶ前に入口で検証する）。
  • SQLでMarkdown向けのエスケープや表示用の連結をする（スナップショットにMarkdownの記法が混ざる）。
  • 判定をするドメインサービスが、警告をログへ直接出す（通知を値で返し、出力は呼び出し側に任せる）。
  • ループの中で毎回TableNamePatterns.of(…)のような値オブジェクトを組み立て直す（入口で1回組み立てて使い回す）。
  • DB由来の名前をPath.resolveやString.formatで直接パス・Markdownにつなぐ（…Locations・OutputPathResolverと、エスケープの部品を通す。10章の「DB由来の文字列を信頼しない」）。
  • CLI引数・設定値・接続URLの値を、例外のメッセージやログにそのまま含める（書き誤りの引数にパスワードが入り得る）。
  • 関数の定義本体を読むコードに正規表現を使う、定義本体の字句の読み取りで例外を投げる（DB由来の入力でバックトラックによる極端な遅さ・処理の中断を招く。9.9節）。
  • InsightWriter以外でファイルを削除する、削除の対象を広げる（ファイルの削除は、前回のfunctionTableUsages.jsonを1つ消す1箇所だけで、ArchitectureTestがInsightWriter以外のdeleteFileの呼び出しを検知する。ディレクトリの削除は--rm-distの出力先だけ）。
  • プレビューの機能の結果を、スナップショットに入れる（--checkの比較対象が変わり、互換性の対象外のものを契約に混ぜることになる）。

13用語集

利用者向けのドキュメントでの呼び方とコード上の名前の対応です。全体はdomain-model.mdの用語集にあります。

テーブルキー
TableKey。スキーマ名＋物理テーブル名。テーブルの識別子で、カラム・関連・付帯情報とテーブルを結ぶ。
テーブル
TableEntity。テーブル・ビュー・マテリアライズドビューの総称（区分はTableType）。
詳細情報
TableDetail。1テーブル分のカラム・インデックス・制約。チャンク単位で取得する。
出力対象
ExportTargets。一括取得した軽い情報の組（条件ではなくデータ）。何を出力するかの条件は「出力対象の絞り込み条件」（TargetSelection）と呼んで区別する。
出力対象の範囲
TableScope。設定のschema・table。
テーブル名パターン
TableNamePatterns。table=の記法（ワイルドカード・除外・スキーマ修飾）。観点の所属テーブルの指定でも使う。
出力対象オブジェクト種別
OutputObjectType。設定のtarget.objects（trigger・function・sequence・type）。
1テーブル分の出力内容
TableDefinitionContent。テーブル定義書1ファイル・スナップショット1行分。
関数1つ分の出力内容
FunctionDefinitionContent。関数・プロシージャの定義書1ファイル・スナップショットと参考情報の1件分（関数＋利用しているテーブル）。
プレビューの機能
PreviewFeature（--preview）。精度・出力の形を固めている途中で、付けたときだけ動く機能。互換性の対象にせず、スナップショットは変えない。
利用しているテーブル
FunctionTableUsage・TableUsage・FunctionTableUsageAnalyzer。関数・プロシージャの定義本体から機械的に抽出した、利用している出力対象のテーブルと操作。呼び出し先の関数・動的SQLの中は含まない参考値。
操作（C・R・U・D）
CrudOperation。利用しているテーブルへの作成・読み取り・更新・削除。TRUNCATEはD、MERGEはWHEN句の操作。
スキーマが決まらない名前
SchemaResolution・TableUsage.schemaCandidates。スキーマ修飾が無く、定義からは決まらない名前（search_path・current_user・synonym）。同じ名前の出力対象のテーブルがあるスキーマを候補として示し、決めつけない。
動的SQL
DynamicSqlKind。実行時に組み立てるSQL（EXECUTE・EXECUTE IMMEDIATE等）。中の参照は抽出できないため、含むことだけを示す。
字句（トークン）
SqlToken。定義本体を、空白・コメントを除いて分けた最小の単位（SqlLexerが作る）。
DBMS種別
Dbms。接続先のDBMS（PostgreSQL・Oracle）。基本情報に出す表示名と、定義本体の字句の規則の切り替えに使う。
関連
ForeignKeyEntity・ForeignKeys。外部キー（物理、RelationType.PHYSICAL）と論理リレーション（論理、LOGICAL）の総称。クラス名は歴史的経緯でForeignKey。
論理リレーション
DBに制約が無く、サイドカーYAMLのrelationsで宣言した関連。ER図では破線。
被参照の関連
incomingRelations・ForeignKeys.referencingTo。自分を参照している関連（自己参照を除く）。
多重度
Cardinality。参照元の外部キー列の一意性とNOT NULLから決まる、関連の両端の件数の関係。
描画距離
output.erDiagramDistance・DiagramNeighborhood。テーブル定義書のER図に描く関連の段数。1は自テーブルの関連だけ。図が上限を超える場合は縮める。
ビューが参照するテーブル／参照しているビュー
ViewReferenceEntity・ViewReferences。ビュー・マテリアライズドビューが参照するテーブル（referencedTables）と、その逆向き（referencingViews。MCPではreferencedByViews）。DBの依存関係から取得する。
ノード
ER図に描くテーブル。関連を持つテーブルだけを数える。
グループ
ForeignKeyGroup。1枚のER図に描く関連のまとまり。上限を超えると連結成分ごとにまとめ直す（ForeignKeyGroups）。
関連カラム
関連の参照元・参照先として使われるカラム。ER図の箱（DiagramBoxes）に表示する。
サイドカー
Sidecar。DBに無い情報を書くYAML（設定のキーはannotations、コード上はsidecarPath）。手動付帯情報・論理リレーション・観点を持つ。
手動付帯情報
Annotations・TableAnnotation。テーブル説明・テーブル備考・カラム備考。
孤児付帯情報
実在しないテーブル・カラムに対する付帯情報。リネーム・削除の見落としとして警告する。
観点
Viewpoint。業務ドメイン別にテーブルをまとめる切り口。観点ページと観点一覧になり、スナップショットには含めない。
突き合わせの通知
ConsistencyNotice。出力対象と関連・付帯情報・観点を突き合わせた結果。重要度に応じてログへ出す。
基本情報
BaseInfoEntity。各ドキュメントの先頭に載せるRDBMS（メジャーバージョンを添える）・DB名・作成日。作成日はDBではなくClockから。
チャンク
詳細情報をまとめて取得・出力するテーブルの塊。大きさは設定のchunkSize（既定3000、0以下でスキーマ全体）。
Sink
ExportSink。取得した情報を1つの出力形式で書き出すもの。Markdown・スナップショット・参考情報の3つ。
スナップショット
domain.model.snapshot。取得結果を構造化したJSON Lines。生成日を含まず、--checkの比較対象で、mcp-serverの入力。
参考情報（insights）
domain.model.insight。スナップショットの事実とは別にAIへ渡す情報（観点と、--previewのときの関数の利用しているテーブル）。--checkの対象外。
利用者が直せる誤り
UserCorrectableException。設定・入力・実行環境を見直せば解消する失敗。報告にスタックトレースを含めない。
