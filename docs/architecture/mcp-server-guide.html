1事前知識：MCPのしくみ

MCP（Model Context Protocol）は、AIアプリケーション（Claude Code、Claude Desktop等）が外部の道具やデータに接続するための通信規約です。登場人物は3者います。

  • ホスト：利用者が操作するAIアプリ。Claude Codeそのもの。
  • クライアント：ホストの中で、1つのサーバーとの接続を受け持つ部品。サーバー1つにつき1つ。
  • サーバー：道具を提供する側。このリポジトリのmcp-serverはこれにあたります。

やり取りするメッセージはすべてJSON-RPC 2.0です。idを持つ「要求」には必ず同じidの「応答」（resultかerror）を返し、idを持たない「通知」には応答しません。

stdioトランスポート：標準出力はプロトコル専用

MCPにはメッセージの運び方（トランスポート）が2種類あり、このサーバーはstdioを使います。クライアントがサーバーを子プロセスとして起動し、標準入力に要求を書き込み、標準出力から応答を読みます。1行が1メッセージです。

1回の接続の流れ

接続は「初期化 → 発見 → 実行 → 終了」の順に進みます。サーバーが能動的に何かを送ることはなく、すべてクライアントからの要求への応答です。

実際の初期化のやり取りです（instructionsは途中で省略）。

→ stdin
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"probe","version":"1.0"}}}
← stdout
{"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-06-18",
  "capabilities":{"logging":{},"resources":{"subscribe":false,"listChanged":false},"tools":{"listChanged":false}},
  "serverInfo":{"name":"dbxray","version":"0.2.0"},
  "instructions":"DBのテーブル定義（dbxrayが出力したスキーマのスナップショット）を調べるサーバー。全体像はlist_schemas、…"}}

tools.listChanged:falseは「起動後にツールの一覧は変わらない」という宣言です。resourcesも同じく一覧は変わらず、購読（subscribe）にも対応しません。スナップショットは起動時に読んだまま変わらないためです。loggingはSDKが自動で付け加える能力で、このサーバーは使っていません。versionはjarのマニフェストのImplementation-Versionで、jar以外から起動するとdevになります。

ツール：定義・結果・2種類のエラー

MCPのサーバーが提供できるものは3種類（ツール・リソース・プロンプト）あり、このサーバーはツールとリソースを提供します（プロンプトは無し）。中心はツールで、「AIが自分の判断で呼ぶ関数」です。リソースは次の節で扱います。

ツールの定義（tools/listで返る）

  • name・title：呼び出し名と表示名
  • description：AIが使い分けを判断するための説明文
  • inputSchema：引数のJSON Schema
  • annotations：readOnlyHint等。クライアントが許可の確認画面などで使うヒントで、保証ではありません

ツールの結果（tools/callで返る）

  • content：結果の配列。このサーバーは常にテキスト1件で、中身はJSONの文字列です
  • isError：ツールとして失敗したか

JSONの中にJSONの文字列が入る二重構造になるのは、このためです。

エラーには2つの経路がある

ツールのエラー（resultの中でisError: true）は、AI自身が読みます。「テーブルemployeが見つかりません。名前の似たテーブル: …」のように直し方を書いておけば、AIは引数を直して呼び直せます。このサーバーは、引数の誤りをすべてこちらで返します。

プロトコルのエラー（JSON-RPCのerror）は、存在しないツール名や不具合のときに返ります。AIに届くとは限りません。

→ 見つからない名前（ツールのエラー。ObjectResolverが文言を作る）
{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"get_table","arguments":{"table":"employe"}}}
←
{"jsonrpc":"2.0","id":4,"result":{"isError":true,"content":[{"type":"text",
  "text":"テーブルemployeが見つかりません。名前の似たテーブル: testdb:sample.employee, testdb:sample.employee_directory_view, …"}]}}

→ 存在しないツール（プロトコルのエラー。SDKが返す）
{"jsonrpc":"2.0","id":22,"method":"tools/call","params":{"name":"no_such_tool","arguments":{}}}
←
{"jsonrpc":"2.0","id":22,"error":{"code":-32602,"message":"Unknown tool: invalid_tool_name","data":"Tool not found: no_such_tool"}}

リソース：利用者が会話に添付するもの

ツールが「AIが呼ぶもの」なのに対し、リソースは利用者（またはクライアント）が選んで会話に載せるデータです。Claude Codeのターミナル版なら@、VS Codeなら「コンテキストの追加…」→「MCP リソース」の候補に並び、利用者が選ぶと中身がそのまま会話に添付されます。AIの判断に依らず、利用者が指名したテーブルの定義を確実に載せられるのが利点です。

このサーバーは、スナップショットの全テーブル（ビューを含む）を1つずつ具体的なリソースとして列挙します（URIテンプレートは使いません。理由はdocs/architecture/mcp-server.mdの「URIテンプレートと補完を出さない理由」）。読むと、get_tableを絞り込み無しで呼んだ場合と同じJSONが返ります。

→ 一覧（テーブルの数だけ並ぶ。先頭の2件）
{"jsonrpc":"2.0","id":3,"method":"resources/list"}
←
{"jsonrpc":"2.0","id":3,"result":{"resources":[
  {"uri":"dbxray://testdb/sample/department","name":"sample.department","title":"sample.department",
   "description":"sample.department / testdb / table / 社内の組織単位を管理するマスタテーブル。 従業員（employee）は必ずいずれか1つの部署に所属する。",
   "mimeType":"application/json"},
  {"uri":"dbxray://testdb/sample/employee","name":"従業員 (sample.employee)","title":"従業員 (sample.employee)",
   "description":"従業員 (sample.employee) / testdb / table","mimeType":"application/json"}, …]}}

→ 読み出し（textはget_tableと同じJSONの文字列）
{"jsonrpc":"2.0","id":4,"method":"resources/read","params":{"uri":"dbxray://testdb/sample/employee"}}
←
{"jsonrpc":"2.0","id":4,"result":{"contents":[{"uri":"dbxray://testdb/sample/employee","mimeType":"application/json",
  "text":"{\"schema\":\"sample\",\"name\":\"employee\",\"logicalName\":\"従業員\",\"type\":\"table\",\"columns\":[…]…}"}]}}

→ 一覧に無いURI（プロトコルのエラー。SDKが返す）
{"jsonrpc":"2.0","id":14,"method":"resources/read","params":{"uri":"dbxray://testdb/sample/nope"}}
←
{"jsonrpc":"2.0","id":14,"error":{"code":-32002,"message":"Resource not found","data":{"uri":"dbxray://testdb/sample/nope"}}}
  • nameは論理名 (スキーマ名.物理名)（論理名が無ければスキーマ名.物理名）。クライアントの絞り込みはname・description・URIが対象で、titleは対象外のため、論理名・物理名のどちらでも探せるようnameに両方を入れています。
  • descriptionの先頭にもnameを入れるのは、Claude Codeの候補がURIを途中で切り、nameよりdescriptionを優先して表示するためです（120文字で切り詰め）。
  • URIの各区間（DB名・スキーマ名・テーブル名）はパーセントエンコードします。DB由来の名前は/・空白・日本語を含み得るためです。name・descriptionも、制御文字・改行・書字方向を変える制御文字を空白に置き換えて1行にします。

サーバーの組み立て方

SDKのサーバーはBuilderで組み立てます。このリポジトリでSDKのサーバーAPIに触るのは、McpServerMain.startのこの部分だけです。

final McpJsonMapper jsonMapper = new JacksonMcpJsonMapper(new ObjectMapper());
McpServer.sync(new StdioServerTransportProvider(jsonMapper))   // 同期版のBuilder。stdioで1セッション
    .serverInfo(SERVER_NAME, version())
    .instructions(INSTRUCTIONS)
    .capabilities(ServerCapabilities.builder().tools(false).resources(false, false).build())
    .jsonMapper(jsonMapper)
    .tools(new TableDefinitionTools(catalog).specifications())          // List<SyncToolSpecification>
    .resources(new TableDefinitionResources(catalog).specifications())  // List<SyncResourceSpecification>
    .immediateExecution(true)                                   // 2.4節
    .build();                                                   // ここで標準入力の読み取りが始まる

ツール1つはSyncToolSpecificationで表します。中身は「ツールの定義（Tool）」と「呼ばれたときの処理（callHandler）」の組です。callHandlerの型は(McpSyncServerExchange, CallToolRequest) → CallToolResultで、exchangeはクライアントへ逆に問い合わせるための窓口ですが、このサーバーは使いません。リソース1つも同じ形のSyncResourceSpecificationで、「リソースの定義（Resource）」と「読まれたときの処理（(exchange, ReadResourceRequest) → ReadResourceResult）」の組です。

SDKの中で起きること

  • 同期APIは非同期実装の包みです。McpServer.sync(...)で作るMcpSyncServerは内部でMcpAsyncServerを持ち、同期のハンドラをMono.fromCallable(...)で包んで登録します。
  • stdioは専用スレッド2本で動きます。StdioServerTransportProviderはbuild()の時点でセッションを1つ作り、標準入力を1行ずつ読むstdio-inboundスレッドと、標準出力へ書くstdio-outboundスレッド（それぞれ単一スレッドのExecutor）を起動します。
  • main()はすぐ戻ります。build()の後にmain()は終わりますが、上の2本はデーモンでないスレッドなのでJVMは動き続けます。標準入力がEOFになると読み取りが終わり、スレッドが片付いてプロセスが終了します。
  • 要求の振り分けはSDKのMcpServerSessionがmethod名で行います。tools/callなら、名前でツールを探し、2.5節の入力検証をしてから、登録したcallHandlerを呼びます。resources/readなら、URIが完全一致するリソースを探して読み出しのハンドラを呼び、無ければ-32002 Resource not foundを返します。

immediateExecution(true) の理由

既定（false）のとき

ツールのハンドラとリソースの読み出しをboundedElasticの複数スレッドで並行に実行します。並行に終わった複数の応答が、別々のスレッドから同時に出力用のシンク（Reactorのunicastシンク）へ書き込まれます。unicastシンクは同時書き込みを受け付けずtryEmitNextが失敗し、その応答は送られません。クライアントは応答を待ち続けて止まります（java-sdk#686）。

true にしたとき（このサーバー）

ハンドラをstdio-inboundスレッドでそのまま1つずつ実行します。書き込みが重ならないため止まりません。ツールもリソースの読み出しもメモリ上の検索だけで速いので、直列でも実用上の影響は小さい、という判断です。回帰はMcpServerProcessTest#respondsToPipelinedToolCalls（ツール）と#respondsToPipelinedResourceReads（リソース）が、応答を待たずに続けて呼んで確かめています。

修正はSDKのmainに入っていて未リリース（docs/architecture/mcp-server.mdの記述）。修正版が出たらimmediateExecutionを残すかを判断する、とされています。

SDKが先に行う入力検証

SDKはcallHandlerを呼ぶ前に、argumentsをinputSchema（JSON Schema）で検証します（ToolInputValidator。validateToolInputsの既定はtrue）。型・enum・minimum/maximum・required・additionalProperties:falseに反すると、ハンドラは呼ばれず、SDKが英語の文言でisError: trueを返します。

→ get_related_tables の depth は inputSchema で maximum 3
{"name":"get_related_tables","arguments":{"table":"employee","depth":4}}
← SDKが返す（ToolArgumentsの「1〜3の整数を指定してください」には届かない）
{"isError":true,"content":[{"type":"text","text":"Tool (get_related_tables) input validation failed: Validation failed: JSON schema validation errors: [/depth: must have a maximum value of 3]"}]}

引数の検証は役割分担です。型・範囲・enum・未知の引数はSDKが入力スキーマで検証し、これを正とします。自前のToolArgumentsは、スキーマで表せない検証（空白を除いた後の空、件数の上限、大文字小文字を区別しない選択肢の照合など）だけを行います。

ServiceLoader と shadowJar

SDKは既定のJSON実装（McpJsonMapperとJsonSchemaValidator）をjava.util.ServiceLoaderで探します。マッパーはMcpServerMainが明示的に渡していますが、入力検証器は渡していないため、mcp-json-jackson2のjarのMETA-INF/services/…JsonSchemaValidatorSupplierから見つけています。見つからなければ起動時にServiceConfigurationErrorで失敗します。

配布用の1つのjar（shadowJar）に依存を詰めると、同名のMETA-INF/servicesファイルが上書きされて登録が消えることがあります。build.gradleのmergeServiceFiles()はそれを防ぐ設定で、McpServerProcessTestが実物のjarを子プロセスで起動して確かめています。

mcp（直下）入口。起動引数の検証、読み込みの呼び出し、SDKの起動
mcp.snapshotsnapshot/のJSON Linesを読み、SchemaCatalogを組み立てる

おすすめの読む順

上から順に読むと、外側（起動とMCP）から内側（ルール）へ進めます。

  1. McpServerMain：何をどの順で組み立てるか。INSTRUCTIONSでツールの全体像もつかめます。
  2. TableDefinitionTools：ツールクラス12の並び＝クライアントに見える順。
  3. ToolSpecifications.readOnlyTool：全ツール共通の包み。引数の誤りがisErrorになる場所です。
  4. SchemaTools：小さなツールクラスで「型」をつかみ、続けて一番大きいTableTools。get_tableの結果の加工はTableOutputBuilderに分かれています。
  5. ToolArguments・ObjectResolver・Page：ツールクラスが共通で使う部品。
  6. SchemaCatalog：組み立てと、関心ごとの窓口（tables()・functions()・sequences()・types()・viewpoints()・functionTableUsages()・relations()・junctions()）の一覧です。続けてTableCatalog・ObjectCatalog・ViewpointCatalogの公開メソッドを見ると、ツールから見たcatalogの全機能がつかめます。
  7. TableFilter・SearchQuery・RelationGraph：テーブルの絞り込み、点数づけ、幅優先探索。7章の図と合わせて読むと速いです。
  8. SnapshotDirectoryReader：ファイルからEntryができるまで。6章参照。
  9. DiagramTools・MermaidErDiagram、TableDefinitionResources：ツールの型から外れる2つ。結果にMermaidの記述を入れるER図（7.9節）と、AIではなく利用者が選ぶリソース（1章）です。
  10. JunctionDetector・SimilarTableFinder・ImpactAnalyzer：スナップショットに無い値を導く・既存の窓口をまとめる、後から足された3つ。中間テーブルの判定（7.11節）、構造の似たテーブルの探索（7.12節）、テーブルの影響範囲の集約（7.13節）です。

4起動の流れ

McpServerMain.mainは次の順に進みます。利用者が直せる誤りはすべてUserCorrectableExceptionで表し、mainの1箇所で捕まえて終了コード2で終わります（cliと同じ方針。ただしcliのクラスとは別物で、mcpパッケージに自前で持っています）。

  1. 標準エラーをUTF-8に固定：System.setErr(new PrintStream(…, UTF_8))。実行環境のロケールで日本語が化けないようにするためです。
  2. 起動引数の解釈：ServerArguments.parse。受け付けるのは--snapshot=<ディレクトリ>1つだけで、未知の引数・重複・空・未指定はすべて誤りです。
  3. 参考情報の読み込み：InsightsDirectoryReaderのreadViewpoints（観点）とreadFunctionTableUsages（関数の利用テーブル。cliを--previewで実行した場合だけある。7.10節）。--snapshotの親の兄弟のinsights/を自分で求めて読みます。ディレクトリ・ファイルが無ければ0件で、誤りにはしません。
  4. スナップショットの読み込み：SnapshotDirectoryReader.readがSchemaCatalogを返します。ディレクトリが無い、database.jsonが1つも無い、新しすぎるformatVersion、JSONとして読めない行、schema・nameの無い行は誤りです（メッセージにファイル名と行番号が入ります）。
  5. 参考情報の合成：catalog.withViewpoints(viewpoints).withFunctionTableUsages(functionTableUsages)。SchemaCatalogは不変なので、観点・関数の利用テーブルを加えた新しいインスタンスを作ります。
  6. 読み込み件数の表示：標準エラーへ[info]:15テーブルを読み込みました。 [snapshot=…]。
  7. SDKの起動：start(catalog)。2章のBuilderでツールとリソース（全テーブル分）を登録して組み立て、build()した時点で標準入力の待ち受けが始まり、mainは戻ります。

I/Oの失敗（UncheckedIOException）は利用者が直せる誤りではないため捕まえません。スタックトレースが標準エラーに出て、終了コードは1になります。

51回のツール呼び出しの流れ

get_tableを例に、標準入力の1行が標準出力の1行になるまでをたどります。灰色の枠がSDK、色の付いた枠がこのリポジトリのコードです。右側は途中で抜ける経路です。

全ツールを包むreadOnlyToolの核心はこの部分です。InvalidToolArgumentExceptionだけを捕まえてisErrorに変え、それ以外の例外はSDKへそのまま投げます。

.callHandler((exchange, request) -> {
  try {
    return handler.apply(new ToolArguments(request.arguments()));
  } catch (InvalidToolArgumentException e) {

6データの持ち方

1行を2通りに持つ

このサーバーを理解するうえで一番効く事実です。スナップショットの1行は、読み込み時に「検索に使う型付きの項目」と「元の1行の文字列（json）」の両方として保持されます。

この設計から、次のことが言えます。

  • 検索に新しい項目を使いたいときだけ、*Lineと*Entryの両方にフィールドを足します。
  • get_tableのsectionsで削れるのはTableSectionのenumに並ぶ9項目（columns・indexes・constraints・foreignKeys・logicalRelations・triggers・definition・referencedTables・referencedByViews）だけです。それ以外（name・logicalName・partitionKeyや将来の項目）は常に残ります。
  • 観点（viewpoints）はスナップショットの項目ではないため、get_tableの結果に後から足されます。sectionsでの絞り込みの対象外です。
  • 関数が利用しているテーブル（tableUsage）も、スナップショットの項目ではなく、参考情報からget_functionの結果に後から足されます。cliを--previewで実行して参考情報がある場合だけで、定義本体のハッシュが一致するときに限ります（7.10節）。
  • 中間テーブルの区分（erRole）・つなぐテーブル（junctionOf）・多対多の相手（manyToMany）も、スナップショットの項目ではなく、主キー・外部キーの構成から組み立て時に導いた値をget_tableの結果に後から足します（7.11節）。観点と同じくsectionsでの絞り込みの対象外で、該当すれば常に返します。
  • テーブルのリソースの中身は、get_tableと同じTableOutputBuilderで組み立てます（sections・columnsの絞り込み無し）。get_tableの結果に項目を足せば、リソースにも同じ項目が載ります。
  • テーブルを参照しているビュー（referencedByViews）もスナップショットの項目ではなく、他のビューのreferencedTablesから逆引きして後から足します（7.5節）。こちらはTableSectionに入っているため、sectionsで選べます。

7catalogの中心ロジック

catalogの各窓口（TableCatalog・ObjectCatalog・ViewpointCatalog）は全オブジェクトをListで持ち、要求のたびに先頭から絞り込みます。あらかじめ作る索引は、RelationGraphの「参照先・参照元」の2つのMapとそこから求めたテーブルごとの関連の数（RelationCounts）、JunctionTablesの中間テーブルの判定結果と多対多の相手（7.11節）、SimilarTableFinderの正規化したカラム名とDBごとのカラム名の数（7.12節）だけです。どれも呼び出しのたびに求め直すと重い、またはスナップショットだけで決まる値です。スナップショットは数百テーブル規模なので、線形の走査で十分という割り切りです。

7.1 名前の解決（get_* と関連ツールの入口）

  1. ObjectReference.of(database, schema, name)：schemaが未指定で名前がsample.employeeの形なら、最初の.で分けてスキーマ修飾とみなします。
  2. ObjectCatalog.lookup<E extends SchemaObject>：DB・スキーマ・名前を大文字小文字を区別せず完全一致で比べます。テーブル・関数・シーケンス・型の4種類がSchemaObjectを実装しているので、この1つの汎用メソッドを共有できます（関数・シーケンス・型はObjectCatalogの窓口から、テーブルは候補の求め方だけを差し替えてTableCatalog.lookupから呼びます）。
  3. 結果は封印インタフェースLookupの3通り：Found（1件）・Ambiguous（複数。キー順）・NotFound（候補付き）。
  4. ObjectResolver.resolveがswitchのパターンマッチで分岐し、Found以外は候補を含む文言でInvalidToolArgumentExceptionを投げます。

見つからないときの候補の求め方は、種類で違います。テーブルは「その名前でsearch_tablesした上位5件」なので、カラム名の一致も候補に入ります（employeにattendanceが出るのはemployee_idカラムがあるため）。関数・シーケンス・型は「名前の部分一致の先頭5件」です。どちらもDB・スキーマの絞り込みを外して探します。

  • AND：どの項目にも含まれない語が1つでもあれば、そのテーブルは一致しません。
  • 語ごとに最大点：1語について、一致した項目の点数の最大値を取り、語ごとの最大値を合計します。
  • 同点：DB名・スキーマ名・テーブル名の順。

7.3 カラムの逆引き（ColumnQuery・find_columns）

強さは「物理名の完全一致 4 ＞ 論理名の完全一致 3 ＞ 物理名の前方一致 2 ＞ 物理名か論理名の部分一致 1」です。match: exact（既定）では3以上だけが残ります。各カラムには、そのカラムが外部キー・論理リレーションで指している先（複合キーなら同じ位置の相手カラム）をreferencesとして添えます。

7.4 関連のグラフ（RelationGraph）

テーブルを頂点、外部キーと論理リレーションを辺とするグラフです。スナップショットには「自分が参照している先」しか書かれていないため、組み立て時に全テーブルを1周して「自分を参照している元」（incoming）の索引を作ります。辺の向きは常に参照元（外部キーを持つ側）→ 参照先です。

relatedTables（get_related_tables）

  • 幅優先でdepth段まで広げる。directionで参照先だけ・参照元だけ・両方を選ぶ。
  • 同じ関連は最初に見つけた段で1回だけ記録する（putIfAbsent）。
  • スナップショットに無い参照先はmissingTablesに分け、その先はたどらない。
  • 自己参照（manager_id）は関連として返るが、訪問済みなので再訪しない。

joinPaths（find_join_path）

  • 向きを問わず幅優先。各頂点への「最短で来た手前の段」をすべて記録する（同じ段からの到達は複数残す）。
  • 終点に届いた段を最後まで処理したら止め、終点から始点へ手前の段をたどり直して全最短経路を集める。
  • limit + 1件まで集め、超えた分があればhasMore: true。
  • 自己参照とスナップショットに無いテーブルは経由しない。

  • incoming：自テーブルを参照しているテーブルの数。多いほど中心のマスタ（サンプルのemployeeは5）。
  • outgoing：自テーブルが参照しているテーブルの数。多いほどトランザクションや中間テーブル（project_assignmentは2）。
  • impact：参照元をRelationCounts.IMPACT_DEPTH（3）段まで幅優先でたどって届くテーブルの数（変更の影響範囲）。被参照の少ない根っこのマスタも拾える（departmentは被参照1だがemployee経由で7）。段数を無制限にすると、大きなDBでは共通のマスタ経由で大半のテーブルに届いて差が出なくなるため打ち切る。

joinsの各要素のfrom・toは関連そのものの参照元・参照先で、たどる向きとは限りません。AIがJOINの条件を書くときはfromColumnsとtoColumnsを同じ位置同士で結びます。グラフの頂点の照合はObjectKeyのequals（大文字小文字を区別する）で、cliが同じ表記で出力する前提に立っています。

7.6 関数のオーバーロードと定義本体

  • SchemaCatalogの組み立て時に、同じObjectKeyのFunctionEntryをFunctionOverloadsへ束ねます（出現順を保つLinkedHashMap）。名前の解決はこの束が単位です。
  • get_functionは既定で定義本体（definition）を除きます。includeDefinition: trueのとき、全オーバーロードの本体が同じなら（Oracleのパッケージ内サブプログラム等）1つにまとめて上位に置き、違えば各オーバーロードに残します。どちらも4,000文字を超えると切り詰め、全体の文字数を書き添えます。getFunctionの中で、共通の本体を求めるsharedDefinitionと、各オーバーロードを切り詰めるtruncateDefinitionOfを順に呼んでいます。
  • オーバーロードごとに、参考情報があれば利用しているテーブル（tableUsage）を足します（catalog.functionTableUsages().find(entry)。7.10節）。定義本体を除いても、FunctionEntry.definitionHashは読み込み時に求めてあるため、照合できます。

7.7 一覧の範囲（Page）

一覧系のツールはまず全件を求めてから、Page.applyでoffsetからlimit件を切り出します。totalは全件数、続きがあればnextOffset = offset + limitを返し、無ければnull（出力されない）です。offsetが全件より大きくても例外にはならず、空のリストになります。件数の既定値100・上限500はPage.DEFAULT_LIMIT・Page.MAX_LIMITにあり、固有の値を持つツール（search_tables・find_columns）以外はこれを使います。

7.8 関連のまとまり（ClusterDetector・list_table_clusters）

観点が宣言されていない範囲で、業務のまとまりの見当を付けるための推測です。使うのは外部キー・論理リレーションのつながりだけで、行数等の統計やテーブル名の接頭辞は使いません。

  1. 範囲を決める：database・schemaで絞り、excludeViewpointTables: trueならいずれかの観点に所属するテーブルを除きます。範囲外のテーブルとの関連は無いものとみなします（RelationGraph.adjacentTablesの結果を範囲で切る）。
  2. 関連の無いテーブルを外す：範囲内に隣が1つも無いテーブルは、まとまりに含めずunrelatedTablesの数だけを返します。
  3. 連結成分に分ける：向きを問わずつながるテーブルの組を1つのまとまりとします。
  4. 大きすぎれば分け直す：maxClusterSize（既定30）を超えるまとまりは、被参照の最も多いテーブルをハブとして除き、残りを連結成分に分け直します。これを繰り返します。ただし、そのテーブルの被参照がTableClusters.HUB_MIN_INCOMING（3）未満なら、一続きの関連を切るだけになるため分けずに残します。
  5. ハブだけとつながるテーブルを寄せる：ハブを除いて1テーブルだけになったものは、被参照の最も多い隣のハブごとに1つのまとまりへ集めます。

7.11 中間テーブルと多対多（JunctionDetector・JunctionTables・erRole・manyToMany）

多対多の関係は、DBには「中間テーブルからの2本の外部キー」という形でしか現れません。AIがprojectとemployeeの関係を知るには、project_assignmentを見つけて2本の外部キーを読む必要があります。そこで、主キー・外部キーの構成から中間テーブルを機械的に判定し、テーブルのER上の区分（erRole: junction）と、中間テーブルを介した多対多の相手（manyToMany）として返します。ClusterDetector（7.8節）と同じく、DBの事実ではなく推測です。

JunctionDetector.detectは1テーブルについて次の順に判定します。

  1. 区分がtableのテーブルだけを対象にする（ビュー・マテリアライズドビューは外す）。
  2. 候補を集める：参照元の列がすべて主キーに含まれる関連（RelationGraph.outgoing。外部キー、論理リレーションの順）を集める。同じ列の組の関連は1本とみなし、先に現れる外部キーを残す。そのうえで、多重度がONE_TO_ONE・OPTIONAL_ONE_TO_ONEの関連（Relation.isOneToOne）を外す。列名は大文字小文字を区別せずに比べる。
  3. 候補が多すぎれば諦める：候補がMAX_CANDIDATES（12）を超えると判定しない。組み合わせを総当たりするため、2のべき乗で増えるのを抑える。
  4. 組み合わせを総当たりする：主キーの列を過不足なく覆い、かつどの関連にも他の関連に無い列がある（外すと覆えなくなる）組み合わせのうち、関連の数が最も多いものを採る。同数なら候補の並びで先のもの。
  5. 2本以上なら中間テーブル：採った組み合わせがMIN_LINKS（2）本以上なら、JunctionTable（テーブルと構成する関連）を返す。

この「外すと覆えなくなる組み合わせのうち最も多いもの」という決め方で、次のような形も扱えます。

形判定理由
主キー以外の列（role・assigned_at等の属性）がある中間テーブル主キー以外の列は問わない
テナントIDを含む複合キー（(tenant_id, a_id)→A、(tenant_id, b_id)→B）中間テーブル関連が列を共有していても、それぞれに自分だけの列（a_id・b_id）がある
主キーに含まれる余分な関連（テナントだけを指す近道の外部キー等）中間テーブル（余分な関連は構成に入らない）余分な関連を足すと「外すと覆えなくなる」を満たさない
同じテーブルを2本の外部キーで参照する（社員の上司・部下の組等）中間テーブル（自己多対多）manyToManyの相手は自分自身になる
3つ以上の親を持つ中間テーブル親どうしがすべて互いの多対多の相手になる
1対1の拡張テーブル（employee_profile）中間テーブルではない1対1の関連は、同じ列の組をまとめた後で数えない
サロゲートキー＋一意索引（idを主キーにし、(a_id, b_id)を一意索引で守る）中間テーブルではないスナップショットの索引は列が構造化されていないため、主キーでしか判定しない
主キーに収まる関連が12本を超える判定しないMAX_CANDIDATES

JunctionTablesは、SchemaCatalog.ofの組み立て時に全テーブルを1回だけ判定し、結果を2つのMapに持ちます。主キー・外部キーの構成から導ける値なので、スナップショットには入れません（RelationCountsと同じ考え方）。

  • find(table)・roleOf(table)：中間テーブルの構成と区分。list_tables・search_tablesの各行のerRole、erRole引数での絞り込み（TableFilter.withJunctionsOnly）、get_tableのerRole・junctionOfに使います。junctionOf（JunctionTable.parents）には、スナップショットに無い親も残します。
  • manyToMany(table)：中間テーブルごとに、つなぐ親どうしを互いの相手として集めたもの（相手・中間テーブルの順）。スナップショットに無い親は、起点にも相手にもしません（get_tableで引けないため）。自己多対多は、テーブルではなく関連の位置で比べて、自分自身を相手にします。

TableOutputBuilderは、manyToManyをMAX_MANY_TO_MANY（20）件までにし、超えると全体の件数をmanyToManyTotalで示します。ほぼすべての中間テーブルの親になる共通のテーブル（テナント等）の結果が膨らむのを防ぐためです。サンプルの実際の結果です（sectionsで絞っています）。

7.12 構造の似たテーブル（SimilarTableFinder・find_similar_tables）

新しいテーブルを作る前に同じ目的の既存テーブルが無いか確かめる、履歴・バックアップ・複製のテーブルを見つける、といった用途のためのツールです。比べるのはカラム名の集合だけで、説明文の近さのような意味の類似は扱いません（呼び出したAIがget_tableで判断します）。基準は既存のテーブル（table）か、設計中のカラム名の並び（columns）のどちらか一方で、SimilarTableQuery.ofTable・ofColumnsが条件を組み立てます。

  1. 比べる相手：範囲（TableFilter。DB・スキーマ・観点）内の、区分がtableのテーブル。基準自身は除く。tableを指定した場合は、基準と同じDBに限る。
  2. カラム名を正規化する：NFKC＋小文字（TextValues.normalize）。正規化で同じ名前になるカラムは先のものを使う。相手のテーブルの正規化は、TableCatalogの組み立て時にSimilarTableFinderが1回だけ行う。
  3. 重みを付ける：カラム名ごとにln((N+1) / そのカラム名を持つテーブルの数)。Nと数は、範囲のDBの区分がtableの全テーブル（基準自身を除く）で数える。範囲内のどのテーブルも持たないカラム名は、1テーブルだけが持つ場合と同じ重みにする。
  4. 重み付きJaccard係数：共通のカラムの重みの合計 ÷（共通＋基準にだけある＋相手にだけある カラムの重みの合計）を百分率にする。カラムが同じ場合（identical）だけを100とし、それ以外は丸めても99にする。
  5. 下限で絞り、並べる：共通のカラム数がminShared（既定3）以上、類似度がminSimilarity（既定50）以上のものを、類似度の高い順・共通のカラムの多い順・名前の順に並べ、limit件を返す。

なぜ重みを付け、なぜDB全体で数えるのか

全テーブルがid・created_at・updated_atを持つDBでは、重みを付けないと、汎用のカラムを共有しているだけのテーブルが似ていると判定されます。持つテーブルが多いカラム名ほど重みを下げて、類似の根拠にならないようにしています（N+1で割るのは、全テーブルが持つカラム名でも重みが0にならないようにするため）。

重みを探す範囲（スキーマ・観点）で数えると、範囲を絞るほどテーブルが減り、汎用のカラムの重みが下がらなくなります。そのため範囲によらずDB全体で数えます。基準自身を数えないのは、tableで指定した場合と、同じカラムをcolumnsで指定した場合の重みを揃えるためです。DBのテーブル数が少ないと効きが弱いのは避けられません。

7.13 テーブルの影響範囲（ImpactAnalyzer・get_impact）

テーブルを変更・削除する前に「何が壊れうるか」を調べるためのツールです。参照元のテーブル・ビュー・トリガー・関数は別々の窓口が持つため、これまではget_related_tables・get_table・get_function・list_triggersを組み合わせて調べる必要がありました。しかも「このテーブルを使う関数」は、tableUsageが関数からテーブルの向きしか返さないため、引く手段がありませんでした。get_impactは、これらをテーブルを起点に1回で集めます。

集めるだけで、スナップショットに無い値は足しません。複数の窓口にまたがるため入口はSchemaCatalog.impactOfで、集め方の規則はImpactAnalyzer（package-private。ClusterDetectorと同じ）が持ち、結果はTableImpact（record）に入ります。呼び出しのたびに求めます。

集め方は5つに分かれ、それぞれ結果の1つのキーになります。

  1. 参照元（affected.referencedBy）：RelationGraph.relatedTables(table, 3, INCOMING)は、テーブルではなく関連を段数つきで返します。段1の関連をdirect（自己参照を含む。参照元のテーブル・種別・関連名の順）に、段1に現れないテーブルをindirect（最小の段数と、その段で見つけた関連の参照先via。段数・テーブルの順）に分けます。同じテーブルが段1と段2の両方に現れる場合はdirectだけに載せ、自テーブルはindirectに含めません。そのため、directの参照元（自テーブルを除く）とindirectを重複なく合わせた数は、list_tablesのimpactと一致します。
  2. ビュー（affected.views）：TableCatalog.viewsReferencingを、ビューを参照するビューまで段ごとに繰り返します。同じビューは1度しか数えないため、循環していても止まります。経由したビューをviaで示します。
  3. トリガー（affected.triggers）：自テーブルのtriggers()です。ビューを調べた場合は、INSTEAD OFトリガーが入ります。
  4. 関数（affected.functions）：同じDBの全関数を関数名（FunctionOverloads）ごとに見て、オーバーロードの参考情報（FunctionTableUsages.find）のUsedTableが、自テーブルまたは2.で集めたビューを指すかをUsedTable.matchesで判定します。一致しなかったオーバーロードのうち、参考情報からは確かめきれないもの（動的SQL・読み切れなかった・解析不可・古い・参考情報なし）は、functions.unverifiedに理由とともに挙げます。
  5. 依存先（dependsOn）：自テーブルのカラムについて、デフォルト値のnextvalが使うシーケンス（SqlNames.sequenceOfDefault）と、型に使われているスナップショットにあるユーザー定義型（SqlNames.typeOfColumn）を、使うカラムとともにまとめます。

なぜ affected と dependsOn を分けるのか

参照元・ビュー・トリガー・関数は「自テーブルを変えると影響を受けるもの」、シーケンス・型は「自テーブルが使っているもの」で、向きが逆です。同じ階層に並べると、AIはどれも影響範囲の一覧として読んでしまいます。キーの名前だけで向きが分かるよう、2つに分けています。

関数の逆引きは、次の規則で求めます。

  • 完全一致：参考情報は出力対象のカタログ上の名前で出力されるため、大文字小文字を区別して比べます（PostgreSQLでは、二重引用符で囲んだ"Employee"とemployeeが別のテーブルになり得ます）。ビューの逆引き（viewsReferencing）と揃えています。
  • 確定と候補：スキーマが決まった名前は確定です。スキーマが決まらない名前（search_path等）は、候補のスキーマに自テーブルのスキーマが含まれる場合だけ候補とし、結果ではmatch: possibleとschemaResolutionで示します。1つのオーバーロードの中で同じテーブルへの一致が確定と候補にまたがる場合は、確定を採ります。
  • 出力の単位は関数と経路：1行は関数名と経路（自テーブルか、使っているビューか）の組で、自テーブルとビューの両方を使う関数は2行になります（usagesTotalもこの行数です）。同名のオーバーロードは1行にまとめ、一致したオーバーロードの引数をoverloadsに並べ、operationsは合算します。Oracleのパッケージで本体をまとめて抽出した場合（overloadsMerged）に、同じ内容が重複して並ぶのを防ぎます。候補になるのは、一致したすべてのオーバーロードが候補でしか一致しなかった場合です。確定のオーバーロードと候補のオーバーロードが混ざる場合はpossibleにならず、候補のオーバーロードの操作もoperationsに合算されるため、確定のように見えます（既知の制約で、FunctionUse.possibleのJavadocに書いてあります）。
  • ビュー経由：参考情報には関数が使うビューも載るため、ビューだけを読む関数も拾います。その行には、使っているビューをviaで付けます。
  • 実行するトリガー：TableCatalog.triggersCallingで、関数を実行するトリガーをcalledByTriggersに付けます。ビューのINSTEAD OFトリガー経由で書き込む関数が、ここで分かります。

参考情報は、動的SQL・呼び出している関数の中・出力対象外のテーブルを含みません。載っていないことが使われていないことを意味しないため、functions.coverageで調べがついた範囲を数えます。同じDBの関数・プロシージャを、参考情報の状態で分けます。

10変更するときの道しるべ

ツールを1つ足すとき

  1. 関心が合う*ToolsクラスにreadOnlyTool(…)を足す。無ければクラスを作り、TableDefinitionTools.specifications()に並べる（並び順はクライアントに見える順）。
  2. 検索・たどりのルールはcatalogの該当する窓口（TableCatalog・ObjectCatalog・ViewpointCatalog・RelationGraph）に置き、その窓口のテスト（TableCatalogTest等）で確かめる（カバレッジ基準の対象）。オブジェクトの種類を足すときはObjectCatalogを使い、SchemaCatalogには窓口を返すメソッドだけを足す。catalogにSDKやJacksonの型を持ち込まない（ArchitectureTestが検出する）。
  3. 型・範囲（minimum/maximum）・enumはinputSchemaに書く。SDKがそれを検証するので、ToolArgumentsでは同じ検査を重ねず、スキーマで表せない検証だけを書く。検証の挙動はMcpServerProcessTestで確かめる（ハンドラを直接呼ぶテストではSDKの検証を通らない）。
  4. 結果は*Outputのrecordにする。コンポーネント名がそのまま結果のキーになる。
  5. McpServerMain.INSTRUCTIONSに使い分けを書き足す。
  6. McpServerProcessTestのツール一覧、TableDefinitionToolsTest、docs/architecture/mcp-server.mdとdocs/usage/mcp-server.mdのツールの表を更新する。

スナップショットの形式が変わるとき

  • 項目の追加は互換です。未知の項目は読み込みで無視され、get_*は元の1行を返すので、何もしなくてもAIに届きます。検索・逆引きに使うときだけ*Lineと*Entryに足します（例：referencedByViewsの逆引きのため、ビューのreferencedTablesをViewReferenceLine・TableEntryに足した）。古いcliのスナップショットには無い項目なので、nullや空を許して読みます。
  • 互換性の無い変更は、cliのDatabaseSnapshot.FORMAT_VERSIONを上げ、SnapshotDirectoryReader.SUPPORTED_FORMAT_VERSIONを追従させます。観点ならViewpointsInsight.FORMAT_VERSIONとInsightsDirectoryReader.SUPPORTED_FORMAT_VERSIONです。
  • cliのベースラインを出し直すと、SampleSnapshotContractTest・SampleInsightsContractTestが追従漏れを検知します（./gradlew :mcp-server:test）。

関数の利用テーブル（プレビュー）の参考情報が変わるとき

  • 項目の追加は互換です。InsightsDirectoryReaderは未知の項目を無視します。get_functionの結果に出したいときだけ、FunctionTableUsageLine・FunctionTableUsageEntryに足し、FunctionTools.tableUsageで組み立てます。互換性の無い変更は、cliのFunctionTableUsagesInsight.FORMAT_VERSIONを上げ、InsightsDirectoryReader.SUPPORTED_FORMAT_VERSION（観点と共通）を追従させます。
  • 定義本体のハッシュの求め方（UTF-8のSHA-256の小文字の16進）は、cliのFunctionTableUsagesInsightとmcp-serverのSnapshotDirectoryReaderに、同じものが1つずつあります。片方だけを変えると、すべての関数でtableUsageが返らなくなります。
  • cliの--previewの差分のベースライン（docs/sample/postgres/output-preview）を出し直すと、SampleFunctionTableUsagesContractTestが追従漏れを検知します（./gradlew :mcp-server:test）。ベースラインのスナップショットは既定のoutput/snapshotから読みます。
  • プレビューの機能なので、互換性の対象外です。tableUsageの説明（ツールの説明）に、参考値であることと、候補のスキーマに決めつけないことを書き続けます。

中間テーブルの判定・構造の類似の規則を変えるとき

  • どちらも判定・計算の規則はcatalogの1クラス（JunctionDetector・SimilarTableFinder）にあり、結果を表すrecord（JunctionTable・SimilarTable）は規則を持ちません。規則を変えたらJunctionDetectorTest・SimilarTableFinderTestに場合を足します（カバレッジ基準の対象）。
  • サンプルでの判定・結果はSampleSnapshotContractTestが確かめています。サンプルのDDLにテーブルを足すと、中間テーブルの判定・多対多の相手・類似の結果が変わることがあるため、このテストとガイドの例を見直します（employee_historyを足したときは、検索・関連の数・まとまり・ER図の例が変わった）。
  • 判定の条件・結果の項目はツールの説明（TableTools・SimilarTableTools）とdocs/usage/mcp-server.mdにも書いてあるため、合わせて直します。どちらもスナップショットに入れない導出した値なので、cliの形式は変わりません。
  • 中間テーブル以外のER上の区分を足すときは、ErRoleに値を足します。入力スキーマのenumはここから作られ、TableTools.tableFilterのswitchが網羅していないとコンパイルが通りません。

影響範囲の集め方を変えるとき

  • 集め方の規則はcatalogのImpactAnalyzerにあり、結果を表すrecord（TableImpact・FunctionUse・FunctionCoverage）は規則を持ちません。ツール側（ImpactTools）は、record・JSONの形と上限、固定文のnotesだけを持ちます。
  • affected.functionsは、cliの--previewの参考情報に依存するため、互換性の約束の対象外です。ツールの説明・結果のfunctions.preview・notes・docs/usage/mcp-server.mdの4か所に「参考値であり、載っていなくても使われていないとは限らない」ことを書き続けます。
  • サンプルでの結果はSampleFunctionTableUsagesContractTest（PostgreSQL）とSampleOracleImpactContractTest（Oracle）が確かめています。サンプルのDDLに関数・トリガー・ビューを足すと、employeeの影響範囲が変わることがあるため、ベースラインを出し直したら、これらのテストを見直します（./gradlew :mcp-server:test）。
  • direct・indirectの分け方を変えるときは、list_tablesのimpact（RelationGraph）との整合を保ちます。ImpactAnalyzerTestと契約テストが、自己参照を含めて確かめています。
  • 関数の参考情報の状態を足すときは、FunctionTableUsages.FreshnessとFunctionCoverageの項目、UnverifiedFunction.Reason、ImpactToolsのCoverage・UnverifiedRef・notesを合わせて直します。
  • リストを足す・分けるときは、ImpactTools.Section（sectionの値とitems）、概要の上限（Affected・Functionsの〜Total）、moreの順を揃えます。sectionの値は、ツールの入力スキーマのenumに使われるため、変えると呼び出し側が壊れます。

ER図の表記・リソースを変えるとき

  • ER図の表記（多重度の端点・線種・箱のカラム・エスケープ）は、cliのMermaidSupportとmcp-serverのMermaidErDiagramの両方にあります。片方だけを変えるとSampleErDiagramContractTestが失敗します。cliを変えたらベースラインを出し直してから、こちらを追従させます。
  • リソースの中身はTableOutputBuilderをget_tableと共有しているため、get_tableの結果を変えるとリソースも変わります。リソースだけを変えたいときはTableDefinitionResourcesで分けます。
  • リソースのname・description・URIの形は、MCPクライアントの絞り込み・表示の挙動に合わせて決めています。変えるときはdocs/architecture/mcp-server.mdの「リソース」の確認結果を読み、実機で確かめます。

やってはいけないこと

  • System.outへの出力や、標準出力へ出すログ設定の追加。プロトコルが壊れます（System.out等への書き込みはArchitectureTestが検出しますが、ログの設定は検出しません）。
  • immediateExecution(true)の削除。SDKの修正版が出るまでは、並行呼び出しで応答が止まります。
  • cliのコードへの依存。両者の接点は、スナップショットと参考情報（insights/）の形式だけです。
  • 関数の参考情報を、定義本体のハッシュで照らさずに返す。片方だけが出力し直された後の、古い抽出結果を最新のものとして答えてしまいます。

11用語集

スナップショット
cliがDBから取得した定義を、機械可読なJSON Linesで出力したもの。{output.path}/snapshot/{DB名}/に置かれる。mcp-serverの唯一の主な入力。
参考情報（insights）
スナップショットとは別に{output.path}/insights/へ出力される補助情報。観点と、関数が利用しているテーブル（cliを--previewで実行した場合だけ）。
観点（viewpoint）
業務ドメイン別にテーブルをまとめる切り口（例：人事管理）。1つのテーブルが複数の観点に所属できる。DB単位でスキーマを持たない。
利用しているテーブル（tableUsage）
関数・プロシージャの定義本体から、cliが機械的に抽出した、利用している出力対象のテーブルと操作（C・R・U・D）。get_functionがオーバーロードごとに返す参考値で、呼び出している関数・動的SQLの中の参照は含まない。
定義本体のハッシュ（definitionHash）
定義本体のSHA-256（小文字の16進）。参考情報が、今のスナップショットと同じ定義本体から抽出したものかを照らすために使う。
プレビューの機能
cliの--previewを付けたときだけ動く、精度・出力の形を固めている途中の機能。出力は互換性の対象外。
スキーマが決まらない名前
スキーマ修飾が無く、定義からは決まらないテーブル名。schemaResolution（search_path・current_user・synonym）と、候補のスキーマ（schemaCandidates）で返す。
中間テーブル（junction）・ER上の区分（erRole）
多対多をつなぐテーブル。主キーの列を、外すと覆えなくなる2本以上の外部キー・論理リレーションで過不足なく覆えるテーブルを、mcp-serverが機械的に判定する（推測）。erRole: junctionで表し、通常のテーブルは区分を持たない。
多対多（manyToMany）
中間テーブルを介してつながる2つのテーブルの関係。get_tableが相手のテーブルと中間テーブル（via）の組で返す。
構造の似たテーブル・類似度
カラム名の集合が似ているテーブル（find_similar_tables）。類似度は、汎用のカラムほど重みを下げた重み付きJaccard係数（%）で、100はカラムが同じ場合だけ。意味の類似ではない。
関連のまとまり（cluster）・ハブ
関連のつながりだけから推測したテーブルの組（list_table_clusters）。人が宣言する観点とは別物。ハブは、大きなまとまりを分けるために除いた、多くのテーブルから参照される共通のテーブル。
外部キー（foreignKey）
DBに実在する制約。関連の由来の1つ。
論理リレーション（logicalRelation）
DBに制約は無いが、サイドカーYAMLで宣言された関連。グラフでは外部キーと同じ辺として扱う。
参照するテーブル（referencedTables）
ビュー・マテリアライズドビューが参照するテーブル（ビューを含む）。cliがDBの依存関係から取得し、ビューの行にだけ入る。逆向きの「参照しているビュー」（referencedByViews）はmcp-serverが逆引きして求める。
メジャーバージョン（majorVersion）
DBMSの版の先頭の数字（例：PostgreSQLの16）。list_schemasが返し、AIが書けるSQLを判断する手がかりにする。古いcliのスナップショットには無い。
多重度（cardinality）
ONE_TO_MANY等。参照先（親）1行に対する参照元（子）の行数を表す。
オーバーロード
同じスキーマ・同じ名前で引数が異なる関数。FunctionOverloadsに束ねる。
ObjectKey・修飾名
DB名・スキーマ名・名前の組。結果ではスキーマ名.名前（qualifiedName）、候補の文言ではDB名:スキーマ名.名前で表す。
ホスト／クライアント／サーバー
MCPの3者。AIアプリ、その中の接続担当、道具の提供側。
トランスポート
メッセージの運び方。このサーバーはstdio（標準入出力）。
inputSchema
ツールの引数のJSON Schema。AIが引数を組み立てる手がかりであり、SDKの入力検証の基準でもある。
リソース
MCPでサーバーが出すデータ。このサーバーでは1テーブルが1リソース（dbxray://…）。AIが呼ぶツールと違い、利用者が@等で選んで会話に添付する。
Mermaid（erDiagram）
テキストで図を書く記法。cliの定義書のER図とget_er_diagramが同じ表記で出力する。
isError
ツールとしての失敗。AIが読んで直せる。JSON-RPCのerrorとは別物。
instructions
初期化の応答でサーバーがAIへ渡す使い方の説明。
immediateExecution
SDKのBuilderの設定。trueでツールを受信スレッド上で直列に実行する。
